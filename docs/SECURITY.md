# Security model

## Trust boundaries

The browser is untrusted. Frontend guards, hidden controls, local storage, route names, and Supabase user metadata are user-controllable and provide no authorization. The BUYSELL API authenticates every private request, resolves the identity to an internal user, authorizes the exact resource, validates input, and computes sensitive values server-side.

## Authentication

Supabase Auth remains the initial identity provider. The frontend uses only the publishable key for auth/session flows. The backend verifies asymmetric JWTs through the project's JWKS with issuer, audience, algorithm, and expiry checks. Legacy symmetric tokens without a suitable key identifier are validated through Supabase Auth's user endpoint using the publishable key. Fail closed when Auth configuration is absent outside an explicitly enabled development mode.

`AuthIdentity(provider, providerSubject)` maps the external subject to the internal `User`. Provider email is informational; it is not an ownership key. Sensitive authorization never uses editable `user_metadata`. Account status, platform roles, store memberships, and explicit permissions are loaded from PostgreSQL. Production must keep `ALLOW_DEV_AUTH=false`.

## Authorization and IDOR protection

Authorization is layered:

- Buyer resources require `resource.userId === req.user.id` (or an equivalent relation).
- Conversation reads and writes require current `ConversationMember` membership.
- Seller routes require an active `StoreMembership` for the route's `storeId` plus the named store permission.
- Platform routes require a `PlatformRoleAssignment` that grants the named permission.
- KYC, disputes, payouts, finance, exports, broadcasts, and internal procurement receive additional purpose-specific checks.
- Resource lookup combines ID and scope in the database query; the API does not fetch globally and check only in the UI.

Store owners have the store wildcard. Platform `SUPER_ADMIN` has the platform wildcard. Other roles receive only the permission map in `backend/src/auth/permissions.js`. Internal sourcing fields require `sourcing.internal.read`; updates require `sourcing.internal.write` or `sourcing.procurement.manage`.

## Data minimization and DTOs

The API returns explicit response shapes. It never serializes raw Prisma graphs. Public catalog DTOs omit seller private data. Order DTOs differ for buyer, participating store, and admin. Public sourcing DTOs omit procurement relations, provider/source details, supplier references, internal costs, exchange assumptions, margin, and operations notes. KYC DTOs omit object keys and provide only authorized, expiring downloads.

Logs redact authorization/cookie headers, passwords, tokens, provider secrets, bank account values, and identity documents. Analytics and push payloads receive identifiers and user-safe copy, not sensitive records.

## Checkout and payments

- Price, coupon, shipping, commission, and total are recalculated from database state in an expiring checkout quote.
- Order creation requires an idempotency key and consumes a quote once inside a serializable transaction.
- Payment initialization loads the order amount; it never trusts an amount supplied by the browser.
- Flutterwave webhooks use the raw request body and a timing-safe HMAC-SHA256 comparison against the configured webhook secret.
- A valid webhook is still only a signal. The backend retrieves the transaction from Flutterwave and validates successful status, exact internal reference, exact currency, and amount at least equal to the expected amount.
- Unique provider IDs and webhook event rows make retries safe. The paid transition and its inventory/ledger effects are atomic.
- Provider payloads returned to users are normalized. Secret keys and raw failure bodies remain server-side.

## Payouts and financial data

Available balance comes from the immutable ledger, not client-side order sums. Payout eligibility and the hold are computed under a transaction lock. Destination account numbers are encrypted at rest and never logged; responses contain only account name and masked digits. Finance administrators cannot bypass the audit log, and approval does not imply that a provider transfer succeeded.

## Files, KYC, and evidence

Upload authorization is purpose-specific and short-lived. The backend validates ownership, MIME allowlist, extension/content consistency where possible, and configured byte limits. Filenames and object keys are generated by the server. Images are decoded/transformed by the media provider where appropriate; active content such as HTML/SVG is not accepted in sensitive upload slots unless separately sanitized.

Product, store, brand, and advertising media may be public. KYC documents, dispute evidence, receipts, private message attachments, and internal sourcing documents are private and are retrieved only through expiring signed URLs after authorization. A database backup is not a media backup.

## API and transport controls

- HTTPS is mandatory outside local development; HSTS and secure hosting headers are enabled at the edge.
- CORS uses an exact allowlist from `FRONTEND_ORIGINS`; wildcard origins are forbidden for authenticated requests.
- The API has a global rate limit plus stricter limits for auth-sensitive, checkout, payment verification, uploads, messages, exports, and webhook endpoints.
- JSON body size is limited. Validation schemas reject unknown/invalid values and enforce bounded pagination.
- Helmet removes common disclosure headers; API errors use stable public codes and never expose stacks, SQL, or Prisma internals.
- Request IDs connect client-visible failures to structured logs.

## Secrets

Secrets live in the deployment platform's encrypted environment store. Never commit database URLs, Supabase secret/service-role keys, Flutterwave secret keys, webhook hashes, Cloudinary secrets, object-store credentials, email keys, VAPID private keys, or procurement credentials. `VITE_*` values are public by definition and may contain only the API base URL, Supabase URL/publishable key, and intentional public configuration.

Rotate a secret immediately if it enters Git history or logs. Rotation and removal from history are separate actions. Production database and provider accounts should use least-privilege credentials and separate development/staging values.

## Database controls

Only the API and migration operator connect to the target commerce database. Runtime credentials use the pooled application endpoint and no schema-migration permission where operationally feasible. Migrations use a direct, separately protected credential. Network/IP restrictions should be enabled where the deployment topology permits them.

During source-system coexistence, any Supabase table left exposed to its Data API must retain RLS and least-privilege grants. `TO authenticated` alone is not ownership authorization; policies require ownership predicates and updates require both `USING` and `WITH CHECK`. Views must be security-invoker or kept out of exposed schemas. Supabase service-role/secret keys never enter the frontend.

## Audit and incident evidence

`AuditLog` records actor, action, target, safe before/after summaries, request ID/IP context, and timestamp for role changes, moderation, KYC decisions, dispute resolutions, payouts, sourcing procurement changes, settings, user suspension, and exports. Payment webhook events retain a payload hash and processing outcome. Audit records must not contain secrets or full identity documents.

Production monitoring must alert on repeated authentication failures, authorization denials, payment verification mismatch, webhook signature failure, payout failures, job retries/dead letters, abnormal export volume, and database readiness failure.

## Release security checklist

- Run dependency audit, lint, tests, secret scanning, and production builds.
- Confirm `ALLOW_DEV_AUTH=false`, source maps policy, exact CORS origins, and no production fixture mode.
- Search frontend output for provider secrets, internal procurement fields, legacy direct database calls, and source-platform branding.
- Exercise cross-account IDOR tests for orders, messages, addresses, seller stores, KYC, disputes, and sourcing.
- Replay a webhook and order request to prove idempotency.
- Confirm private media URLs expire and cannot be reused by another account.
- Verify backups and rollback before schema/data changes.

Report vulnerabilities privately to the repository owner. Do not include live secrets, identity documents, or exploitable customer identifiers in issues.
